## 結論

macOS 15 (Sequoia) 以降の**ローカルネットワーク・プライバシー保護**は、サードパーティのプロセスが
プライベートIP（`192.168.x.x` / `10.x.x.x` など）へ接続するのを拒否します。許可が無いと、こうなります。

```
connect EHOSTUNREACH 10.5.27.109:11235 - Local (10.5.27.4:54035)
```

**ソケットは作れているのに `connect` だけが即座に失敗する**のが特徴です。所要時間は **0〜5ms**。

厄介なのは3点です。

1. **`EHOSTUNREACH`（No route to host）という形で返る** → 「相手が落ちている」「ネットワークの問題」に見える
2. **Apple署名のシステムバイナリは免除される** → **`curl` では絶対に再現しない**
3. **権限は実行バイナリではなく「責任プロセス」に紐づく** → **端末から切り離して常駐させた瞬間に無音で死ぬ**

対処は、**許可を持つアプリの子孫としてプロセスを起動し直す**ことです。

```bash
# 常駐サーバを、許可を持つターミナルアプリから起動し直すだけ
herdr server stop     # 自分の常駐プロセスに置き換えて読んでください
```

以下は、ここに辿り着くまでに**4つの筋を立てて全部外した**記録です。
特に「`curl` で到達性を60回測って全部 200 だったのに原因に辿り着けない」という状態を経験したので、
同じ沼にいる人の時間を節約できればと思います。

## 環境

| | |
|---|---|
| Mac | macOS 27.0 (Build 26A428) |
| 接続先 | 自宅LAN `10.5.27.0/24` 上のサービス（self-hosted クローラ、Grafana、監視など） |
| 落ちたもの | Claude Code の MCP サーバ（SSE 接続） |
| ランタイム | Bun 1.3.4 / Node 22（どちらも同じ症状） |

## 症状

Claude Code の MCP 一覧にこう出ます。

```
Status: ✗ failed
Issue:  SSE error: ECONNREFUSED: Unable to connect. Is the computer able to access the url?
Auth:   ✗ not authenticated
```

`Auth: ✗ not authenticated` と出るので**認証の問題に見えます**。実際は違って、
**繋がらなかったので認証まで到達していない**だけでした。

ログを見ると、失敗までの時間が異様に短い。

```
2026-10-02T06:39:29.282Z  Starting connection with timeout of 30000ms
2026-10-02T06:39:29.290Z  SSE Connection failed after 2ms
```

**2ms は TCP ハンドシェイク＋TLS には短すぎます。** 同じ経路への `curl` は 21ms かかっていました。
つまり**パケットが外に出る前に失敗している**。

## 外した筋、その1 ── サーバ側

まずサーバを疑いました。全部シロでした。

| 確認 | 結果 |
|---|---|
| コンテナの稼働 | 8週間無停止・`RestartCount=0` |
| リバースプロキシ | 8週間無停止・`NRestarts=0` |
| **401 のログ** | **33日間で1件も無し** |
| 認証方式 | 静的Bearerトークン（**期限が無い**）／ サーバ側・コンテナ内・クライアント設定の**3者でハッシュ一致** |

## 外した筋、その2 ── 認証の期限切れ

「認証が失効しているのでは」という筋も消えました。そもそも静的トークンに期限はありません。
JWT も発行はされていましたが、**ツール呼び出しのたびに新規発行**される設計で、失効し得ない作りでした。

## 外した筋、その3 ── DNS

`dig` の結果から「名前解決が不安定なのでは」と考えました。
内向きDNSが `*.example.dev` を静的に即答する設定だったため、**TTL が 0** だったのも傍証に見えました。

```
crawl4ai.example.dev.	0	IN	A	10.5.27.103
```

これは**完全に外れ**でした。URLを **IPアドレス直打ち**に変えて、名前解決が一切介在しない状態にしても、
**同じく 5ms で失敗した**からです。仮説が死んだ瞬間でした。

:::message
TTL 0 の静的応答は、そもそも**キャッシュに乗らず期限切れもしません**。
「DNSキャッシュをパージすれば直るかも」という筋は最初から存在しませんでした。
:::

## 外した筋、その4 ── プロキシ・IPv6・スリープ

- プロキシ: システム設定も環境変数も**全て無効**
- IPv6: AAAAレコード無し、`getaddrinfo` は IPv4 のみ返す、プロキシ先は dual-stack で待ち受け
- スリープ: スリープ抑止が効いていて**一度もスリープしていない**
- `/etc/hosts`: 該当エントリ無し
- ネットワークフィルタ（Little Snitch 等）: システム拡張は HID ドライバのみ

全部シロ。そして **`curl` は 60回中60回成功**していました。

## 決定打 ── 「何で叩くか」を変えて測る

ここで、**到達性ではなく実行主体を変えて**測り直しました。これが効きました。

```js
// Bun / Node から、同じ宛先へ
await fetch("https://example.com");                  // 公開インターネット
await fetch("http://10.5.27.109:11235/health");      // 宅内LAN
```

| 実行主体 | 公開インターネット | 宅内LAN |
|---|---|---|
| **Bun 1.3.4** | ✅ 200 (57ms) | ❌ `FailedToOpenSocket` **0〜1ms** |
| **Node 22** | ✅ | ❌ `EHOSTUNREACH` **1〜5ms** |
| **`/usr/bin/curl`**（Apple署名） | ✅ | ✅ **200** |
| **`/usr/bin/nc`**（Apple署名） | — | ✅ 成功 |
| **`/usr/bin/ssh`**（Apple署名） | — | ✅ 成功 |

**インターネットには出られるのに、LANだけソケットが開けない。**
そして **Apple署名のバイナリだけが通る。** これがローカルネットワーク権限の固有の挙動です。

:::message alert
**ここが最大の罠です。** 切り分けに `curl` を使うと、何度測っても 200 が返ります。
「サーバは正常、経路も正常」という結論にしか辿り着けず、クライアント内部で止まっていることに気づけません。
:::

## 確定 ── loopback は対象外

決め手になったのがこれです。ローカルネットワーク権限は **`127.0.0.1` を対象にしません**。
SSHポートフォワードで、**同じサービス**へ loopback 経由で当ててみます。

```bash
# /usr/bin/ssh は Apple署名なので、これ自体はLANに出られる
ssh -N -L 21235:10.5.27.109:11235 user@gateway
```

```
✅ 200  17ms   http://127.0.0.1:21235/health     ← loopback経由
❌       0ms   http://10.5.27.109:11235/health   ← LAN直  FailedToOpenSocket
```

**同じ Bun プロセスから、同じ瞬間に、同じサービスへ。** 違いは宛先アドレスが
ローカルネットワークかどうかだけ。ここで確定しました。

この性質は**そのまま回避策にもなります**。権限が取れない環境では、SSHトンネルで
`127.0.0.1` に寄せてしまえば動きます。

## 真因 ── 権限は「責任プロセス」に紐づく

ではなぜ権限が無かったのか。macOS は**プロセス生成時に「責任プロセス（responsible process）」を記録**し、
TCC やローカルネットワークの可否を**その責任プロセスの身元**に対して解決します。

壊れていた側のプロセスツリーはこうでした。

```
PID 1 (launchd)
 └─ herdr server   ← PPID=1。端末から切り離された常駐
```

この常駐サーバは **自分自身が責任プロセス**で、しかも ad-hoc 署名の単体 Mach-O。
**バンドルIDが無いので、そもそも許可を与える対象が存在しません。**
System Settings の一覧にも出てきません。

一方、復旧後はこうなっていました。

```
Ghostty.app
 └─ zsh
     └─ herdr
         └─ herdr server   ← 責任プロセス = Ghostty
```

Ghostty は**公証済みの Developer ID 署名**で、`Info.plist` に使用目的も宣言しています。

```bash
$ /usr/libexec/PlistBuddy -c "Print :NSLocalNetworkUsageDescription" \
    /Applications/Ghostty.app/Contents/Info.plist
A program running within Ghostty would like to access the local network.
```

**許可を与えられる正しい形のアプリ**なので、その子孫は許可を継承します。

### 対処はこれだけだった

```bash
herdr server stop     # 許可を持つターミナルから起動し直させる
```

これで、宅内の**全サービス**が一斉に回復しました。

```
✅ 200  15ms  self-hosted クローラ
✅ 200  52ms  同上（ドメイン経由）
✅ 302  15ms  Grafana
✅ 302  13ms  Uptime Kuma
```

:::message
**常駐プロセスは、端末を閉じても生き残ることが価値**です。
ところがローカルネットワーク権限の観点では、それがそのまま「**許可の無い状態で上がり直す経路**」になります。
再起動後・クラッシュ後・自動更新後に無音で死ぬ、という形で再発します。
:::

## 効かなかった対処（全部実測）

遠回りした分を書き残しておきます。

### ❌ `tccutil reset LocalNetwork`

```
tccutil: Usage: tccutil reset SERVICE [BUNDLE_ID]
```

**ローカルネットワーク権限は TCC の管理下にありません。** `LocalNetwork` というサービス名自体が存在しないので、
`tccutil` ではリセットできません。

### ❌ System Settings のトグル

CLIバイナリ単体は `Info.plist=not bound` / `bundle_id: (null)` と評価されるため、
**一覧に出ないか、出てもオンにして `allowed: 0` のまま**です。
Claude Code でもこの件は issue になっていますが、**closed as not planned** で止まっています。

### ❌ ad-hoc署名の `.app` で包む

`NSLocalNetworkUsageDescription` を宣言した `.app` を自作して ad-hoc 署名しても、
**プロンプトすら出ません**でした。

### ⚠️ 実行ファイルがシェルスクリプトの `.app`（誤判定の原因）

ここで一度**「署名しても無駄だ」と誤った結論を出しました**。
原因は自作テストアプリの実行ファイルを**シェルスクリプト**にしていたことです。
スクリプトは `/bin/bash` や `python3`（＝Apple署名のバイナリ）を exec するため、
**責任プロセスが `.app` に乗りません**。

**コンパイル済みの Mach-O** に差し替えて Developer ID 署名すると、結果が変わりました。

```
1回目: NG connect失敗 errno=65 (No route to host)   ← 仕様上、初回は必ず失敗する
2回目: OK connect成功                                ← 以後ずっと通る
3回目: OK connect成功
```

**初回のアクセスは権限判定をトリガーするだけで失敗します。** 1回で諦めると誤判定します。

### ⚠️ Terminal.app だけ試して満足しない

切り分けの途中、`osascript` 経由で **Terminal.app** から試したところ `EHOSTUNREACH` でした。
そこで「ターミナル経由では駄目」と結論して遠回りしたのですが、**実際に使っていた Ghostty は許可済み**でした。

**ターミナルアプリごとに許可の状態は違います。** 一つ試して駄目でも、
**自分が実際に使っているアプリ**で確かめてください。

## 発症はOS更新と同時ではない

最後に、見つけにくさの理由をひとつ。

| 日付 | 出来事 |
|---|---|
| 09-03 | **macOS 27.0 を導入** |
| 09-15 | 接続失敗の初出 |
| 09-22 | 常駐サーバが端末から切り離された状態で起動（この日から急増） |
| 10-02 | 失敗 **1309件** |

**OSを上げた日には何も起きません。** 既に動いていたプロセスはそのまま動き続け、
**何かの拍子に起動し直された瞬間**に、無音で落ちます。
だから「最近OSを上げた」と結びつけるのが難しい。

## まとめ

- macOS 15以降、**サードパーティのプロセスは許可なしに宅内LANへ接続できない**
- 拒否は **`EHOSTUNREACH` / 0〜5msの即死**という「相手が落ちている」ように見える形で返る
- **Apple署名のバイナリは免除** → **`curl` / `nc` / `ssh` では絶対に再現しない**
- 権限は**責任プロセス**に紐づく → **端末から切り離して常駐させると無音で死ぬ**
- **`127.0.0.1` は対象外** → 切り分けにも、恒久的な回避（SSHトンネル）にも使える
- 対処は**公証済みで使用目的を宣言したアプリの子孫として起動し直す**こと

切り分けのとき、`curl` が通ったからといってクライアント側を無罪にしないでください。
**「何で叩くか」を変えて測る**のが、この問題に気づく唯一の方法でした。
